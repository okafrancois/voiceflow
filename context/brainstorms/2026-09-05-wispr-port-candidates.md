# Wispr port candidates for Voice Flow

Date: 2026-09-05

Status: decision inventory. This is not an implementation specification.

## Decision frame

The accepted direction for Home is a useful summary with recent transcription history. The earlier minimal readiness-only Home is no longer the preferred interface. The exact metrics, layout, and number of history rows still need a product decision.

This review compares the [official Wispr research snapshot](./2026-09-05-wispr-official-research.md) with current Voice Flow specs and code. It does not assume that matching Wispr's navigation is the right product choice. Voice Flow is local-first, backend-driven, and centered on accurate dictation and recovery.

Scope labels compare repository impact, not calendar time:

- **S**: one existing contract exposed or reorganized through a small interface change.
- **M**: a new backend query or bounded data contract plus a dedicated interface and tests.
- **L**: a new persistent domain or capture lifecycle that crosses backend, storage, IPC, and UI.

## Recommended interface package

The smallest coherent package is:

1. Home with readiness, a compact local usage summary, and five recent results.
2. Full History as the existing searchable recovery workspace.
3. Dictionary with inspectable automatic corrections and manual vocabulary.
4. Snippets beside Dictionary, using the existing deterministic backend.
5. Simple per-app style assignment backed by current profiles and application rules.

This package makes existing capability legible. It does not require a new capture mode or cloud account system. A separate Stats page and selected-text Transforms can follow once their metric and interaction choices are settled. Scratchpad and meeting capture should each receive a dedicated spec if selected.

## Questions for interface selection

1. Should Home show three compact metrics plus five recent results, or a denser Wispr-like card with streak and WPM?
2. Should Stats be a primary sidebar destination in the first redesign, or should Home link to it as a later screen?
3. Should Dictionary and Snippets share one destination with tabs, or remain separate destinations?
4. Should per-app styles expose a few constrained presets while Advanced retains full profiles, or should the interface expose profiles directly?
5. Should selected-text transforms join the primary navigation now, remain under Advanced, or wait for shortcut and inline-diff support?
6. Is the desired Scratchpad one append-only local note or a multi-note editor?
7. Does “meeting notetaker” mean live system-audio capture or processing a recording after the meeting?

## Evidence limits

No adoption data or comparative accuracy measurements were available. The Wispr side is based on official documentation and may include staged or plan-gated features. Repository evidence establishes implemented contracts and checked-in UI, not current native compatibility in every third-party application. The root review is separately inspecting the installed Wispr build; any observed differences should update the research snapshot before they become requirements.
